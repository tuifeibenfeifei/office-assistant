## 三之二、真实启动路径取证（`--startup-check --full --scan`）

UI 自检刻意跳过了托盘与窗口显示，因此它不能回答"双击之后到底有没有起来"。
为此增加了一个把**用户双击时真正执行的那条链路**完整走一遍并逐步打印轨迹的模式：

```
================ 全能办公助手 · 启动路径取证 ================
  模式：完整启动（含五页初始化与后台服务）
  宿主：就绪（SQLite 3.51.1）
  托盘：已创建
  主窗口可见：True
  初始化状态栏：就绪。所有数据仅存本机；删除统一进回收站，可恢复。
  未完成作业角标：0
  索引概况：索引为空（尚未扫描磁盘）
  真实磁盘扫描：文件 106,600，目录 13,403，25.67 GB，7,984 项/秒，用时 15.03s；首个错误：C:\Users\DefaultAppPool :: 访问被拒绝

  启动轨迹：
    [+  125 ms] 宿主就绪（SQLite 3.51.1，数据目录 …）
    [+  753 ms] 主窗口已构造（XAML 解析完成）
    [+ 1009 ms] 托盘图标已创建
    [+ 2156 ms] 主窗口已显示
    [+ 4940 ms] 开始真实磁盘扫描取证：C:\（只读，条目上限 120,000）
    [+19990 ms] 扫描取证完成：全盘扫描：文件 106,600，目录 13,403，共 25.67 GB，耗时 15 秒（7,984 项/秒），无权限 74

  启动路径验证通过：从数据目录到窗口显示、页面初始化与后台服务都已跑通。
==========================================================
```

运行日志同步落盘，可交叉验证：

```
[INFO ] ========== 全能办公助手 启动 ==========
[INFO ] SQLite 已就绪（系统组件版本 3.51.1）：…\officeassistant.db
[INFO ] 类型规则表已初始化：154 条
[INFO ] 启动：宿主就绪（SQLite 3.51.1，数据目录 …）
[INFO ] 启动：主窗口已构造（XAML 解析完成）
[INFO ] 启动：托盘图标已创建

[INFO ] 学习通自动同步已启动（每 10 分钟）
[INFO ] 合规回归通过：2 项检查全部通过，扫描 2 个程序文件，耗时 6 毫秒。
[INFO ] 资源管家调度器已停止
[INFO ] ========== 应用已退出 ==========
```

**这段取证回答了三个此前悬空的问题：**

1. **能不能启动**：能。宿主、窗口、托盘、五页初始化、后台服务全部就绪，退出码 0（此前只有"不弹窗不报错"的观察）。
2. **真实盘扫描行不行**：行。C 盘 106,600 文件 / 13,403 目录 / 25.67 GB 用 15.03 秒扫完（7,984 项/秒），
   74 个无权限目录被正确计数并跳过，索引落库 73 MB 的 SQLite 文件。
3. **退出干不干净**：干净。日志无告警，托盘设置读取不再在宿主释放后发生。

**启动链路的健壮性同时得到加固**（这是取证过程中发现并修掉的真实隐患）：

| 改进 | 原因 |
| --- | --- |
| `OnStartup` 全链路 try/catch + 分步轨迹 | 原实现里任何异常都会让进程**无声消失**（无日志、无提示），用户看到的就是"双击没反应" |
| 启动异常落盘 `%TEMP%\OfficeAssistant-startup-failure.log` 并弹窗 | 静默死亡是最难排查的故障，必须留下痕迹 |
| 单实例锁失败降级为继续启动 | 命名内核对象在受限策略下可能不可用，不能因此让程序起不来 |
| 托盘创建失败降级为普通窗口 | 托盘依赖通知区域；远程会话或 Explorer 未就绪时不应连界面一起失去 |
| 收尾顺序改为"先置标志再关窗口" | 窗口可能被关闭两次，第二次会去读已释放的数据库并留下无意义告警 |

| 用 `..` 绕过保护规则删除系统文件 | `Normalize` 先折叠路径再比对前缀；自测含 4 种绕过写法全部被拦截 | **拦截** |

| 直接调用删除入口（绕过 UI 确认） | `OperationExecutor.CheckDeletable` 是唯一入口的前置校验，无法绕过；自测直接调用批量删除高危目录 → 整体 `Blocked` | **拦截** |
| 把可执行体放进临时目录后"一键清理" | `EvaluateRisk` 对危险扩展名（exe/dll/sys/msi/脚本/注册表/快捷方式）一律判为危险级，永不进入清单 | **拦截** |
| 库中旧风险值过低导致误删 | `BuildPlan` 用当前防护引擎对每条候选重新判定，不信任库中值 | **拦截** |
| 用户白名单被清空后失去保护 | 系统目录保护是硬编码前缀集合，与用户白名单互不依赖 | **不失效** |
| 回收站被禁用/不可用 | 明确报错并要求用户决定；**不静默降级为永久删除** | **安全失败** |
| 把目录移动进自己的子目录 | `Move` 前置校验源/目标包含关系 | **拒绝** |
| 目标已存在同名项 | 返回 `Conflict` 状态，UI 二次确认后才可覆盖（覆盖也是先移入回收站） | **安全** |
| DPAPI 密文文件被拷到别的账户/机器 | DPAPI 绑定当前 Windows 账户，解密失败 → 提示重新登录，不静默重试 | **安全失败** |
| 平台上出现会话失效 | 返回 `SessionExpired` 并提示重新登录，指数退避，不静默重试 | **安全失败** |
| 恶意/异常的 JSON 响应 | 用 `JsonDocument` 逐字段安全读取，类型不匹配返回空值；解析失败按失败处理 | **不崩溃** |
| 符号链接/联接形成环 | 默认不跟随重解析点，并登记为危险级条目；同轮 `visited` 集合去重 | **不循环** |
| 目录权限不足 | 计数为“无权限”并登记为不可访问条目，不中断整轮扫描 | **降级** |
| 超大目录/极多文件拖垮系统 | 工作线程 `BelowNormal` 优先级、`MaxEntries` 安全阀、可随时中止 | **可控** |
| 误删后想恢复 | 所有删除统一 `FOFX_RECYCLEONDELETE` 进回收站；操作日志与审计日志双份留痕 | **可恢复** |

## 六、开发过程中由测试发现并修复的缺陷

以下缺陷都是**先被自动化拦住**、再定位修复的，列出以便复核：

| # | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | 进程直接崩溃，退出码 `0xC0000409`（STATUS_STACK_BUFFER_OVERRUN） | 系统组件 `winsqlite3.dll` 的 `sqlite3_exec` 在本机触发栈保护失败 | 完全不绑定 `sqlite3_exec`，`Exec()` 改为按分号切分后逐条 `prepare + step` |
| 2 | 数据库读回文本错乱（`a.txt` → `\n txt`） | 文本绑定使用 `SQLITE_STATIC`，SQLite 不复制内容，而调用方立即释放了缓冲区 | 全部文本/二进制改用 `SQLITE_TRANSIENT` |
| 3 | 全盘扫描文件数恰好翻倍（460 vs 230） | 一级子目录既被卷根分片递归遍历、又作为独立分片遍历 | 建立共享 `shardPaths` 集合，分片登记后卷根不再下钻 |
| 4 | 增量扫描统计偏小 11.7%（203 vs 230） | 扫描根目录按"直接子项数"指纹被整棵跳过，而跳过值语义是子树计数 | 分片根始终遍历一次，其余目录走跳过路径（`isScanRoot` 语义修正） |
| 5 | 增量扫描从未跳过任何目录（增量等于全量） | 分片根以 `parentChanged=true` 启动，使跳过条件恒不成立 | 用 `isShardRoot` 取代 `parentChanged`，语义与实现对齐 |
| 6 | `%TEMP%` 下的临时文件被判为"系统目录已保护"，无法清理 | 临时目录位于用户配置目录之下，受保护前缀先命中 | 临时目录作为唯一例外：`IsTempArea()` 前置判定 |
| 7 | `docx/xlsx` 被识别为"压缩包"（识别正确率仅 60%） | 文件头 ZIP 判定优先于扩展名规则 | 引入"扩展名↔文件头兼容性"判定：冲突时以文件头为准并提示改名，兼容时以扩展名为主 |
| 8 | 合规自检假阳性：11 个源文件命中关键字「TDI」 | 关键字过短，在 `stdint` 等无关标识符中出现 | 关键字改为完整 API 名/文件路径，并增加"危险注册表动作 + 敏感目标"组合规则 |
| 9 | UI 自检报错：只读属性 `ProgressPercent` 参与 TwoWay 绑定 | `ProgressBar.Value` 默认 TwoWay，绑定到只读计算属性 | 显式 `Mode=OneWay`（3 处进度条） |
| 10 | UI 自检报错：只读属性 `IsCronMode` 参与 TwoWay 绑定 | 同上，`RadioButton.IsChecked` 默认 TwoWay | 显式 `Mode=OneWay`，并把调度模式改为可写属性驱动派生属性 |
| 11 | 包管理器镜像列表在界面上空白并产生 12 条绑定错误 | `IReadOnlyList<(string,string,string)>` 的元组字段是 `Item1/Item2`，WPF 无法按 `Name/Command/Note` 访问 | 改为 `PackageMirrorEntry` 记录类型（具名属性） |
| 12 | 关闭窗口时崩溃：`SQL 预编译失败：连接已关闭` | 托盘退出路径已释放宿主，随后窗口关闭流程又读取了设置 | `PrepareShutdown` 改为幂等；`OnClosing` 对设置读取加保护并区分自检模式 |
| 13 | 自检期间死锁（`InitializeAsync` 永远不返回） | 在 UI 线程上 `GetAwaiter().GetResult()`，而初始化链路需要回到 UI 线程 | 改用 `DispatcherFrame` 消息泵等待任务完成 |
| 14 | 启动链路任何异常都会让进程**无声消失** | `App.OnStartup` 没有兜底：WPF 在 OnStartup 抛异常时直接终止，既无日志也无提示；用户看到的现象就是"双击没反应"，且无从排查 | 全链路 try/catch + 分步启动轨迹；失败时把报告写入 `%TEMP%\OfficeAssistant-startup-failure.log` 并弹窗；单实例锁与托盘分别降级 |
| 15 | 收尾日志出现"读取托盘设置失败：连接已关闭" | 应用关闭时会再次关闭窗口，此时宿主已释放，`OnClosing` 仍去读设置 | `OnClosing` 先判断收尾标志；收尾顺序改为"先置标志并释放宿主、再关窗口" |

> 第 14、15 项的发现过程值得一提：为了回答"双击到底能不能起来"，我新增了 `--startup-check` 取证模式，
> 把真实启动链路的每一步打印出来。取证本身成功了，但顺带暴露出"失败时没有任何痕迹"这一更严重的问题——
> 也就是说，即便当初启动真的失败，用户和开发者都拿不到任何线索。这个隐患比"某次没起来"更值得修。

## 八、结论

- **可运行性**：已由 `--startup-check --full` 取证确认——宿主、主窗口、托盘图标、五页初始化与后台服务全部就绪，
  退出码 0，退出日志无告警。**"双击能不能起来"这个此前唯一悬空的核心问题已经闭环。**
- **功能三（核心）**：扫描（真实 C 盘 10.6 万文件 / 25.67 GB / 15 秒）、增量、识别、误删防护、一键清理、
  未识别区、操作审计 —— 引擎层、UI 装配与真实磁盘性能均已实测通过；拖拽交互的自动化用例待交互式桌面补测。
- **功能四**：调度、阈值、豁免、报告 —— 逻辑与安全断言已通过；效果数值（释放量、常驻内存）需真实环境测量。
- **功能一**：合规红线已通过**源码 + 二进制双向回归**；镜像/配置/代理三项写入均带快照与一键还原；
  加速比与配置往返需真实环境实测。
- **功能二**：凭据安全、状态合并、提醒去重、频率控制、降级行为已通过；
  真实平台同步依赖使用方提供接口端点。
- 最高优先级的两项（**误删防护**与**合规红线**）已由自动化测试覆盖并全部通过。
